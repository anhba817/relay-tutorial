<ChapterHeader id="3.9" locale="vi" />

Channel có hai loại từ chương 2.1.

```sql
CONSTRAINT channels_type_check CHECK (type IN ('public','private'))
```

Hai mươi hai chương sau, column vẫn chứa `'public'` ở mọi row của mọi environment. Chương
trước xây `POST /v1/channels` và cho field enum một giá trị—`z.enum(["public"])`—vì
endpoint nhận `private` sẽ bán một guarantee platform chưa giữ.

Quyết định đó đúng, nhưng lý do được nêu hơi sai. Claim là *không gì đọc column*; đếm
reference có mười một: `ChannelRow` khai báo nó, hai repository query select nó, và
`channels.controller.ts` trả nó trong create response. Trả column cũng là đọc. Điều đúng
hơn và sắc hơn: **không decision nào consult nó.** `.type ===` duy nhất trong non-test
code thuộc protocol frame, không phải channel.

Mười lăm analysis pass đọc cụm “năm dead column” mà không đo count. Một lệnh `grep` sửa
nó, đồng thời làm statement mạnh hơn: giá trị có thể visible với mọi client mà vẫn không
authorize điều gì.

<Why source="docs/04-srs.md FR-CHN-05">

FR-CHN-05 chỉ có một câu: message của private channel chỉ visible với member. Việc không
nằm ở câu đó mà ở bốn cửa của “visible”: send path, read-by-id, history và socket session.
Guarantee chỉ mạnh bằng cửa yếu nhất. Chương này chỉ widen enum **sau cùng**, khi cả bốn
đã giữ—ngược với thứ tự trực giác.

</Why>

## Verb không có handler

Trước khi viết một dòng, hãy hỏi: mọi verb phải tuân rule mới đã có nơi để tuân chưa?

`GET /v1/channels/:channelId` chưa tồn tại. Controller chỉ có create và add member; customer
tạo channel mà không đọc lại được bốn field. Ba document dựa trên route đó: success
criterion gọi “read by id” là một trong bốn verb, requirement nói “every read”, và contract
có một row dành cho nó.

Không ai phát hiện bằng cách so spec với plan và task. Câu hỏi đúng cho repository là có
hoặc không: *verb này có handler không?* Hai trong tám critical finding của feature đến từ
kiểu câu hỏi ấy.

<Trap>

Bốn table trong task list—route theo handler/credential/repository method/pin, column theo
migration/writer/reader/removal test—khép lớp defect này và chỉ lớp đó. Chúng không hỏi
route có khớp acceptance scenario khiến nó cần tồn tại không. Một pass riêng tìm ra
requirement bulk removal “tối đa 100 mỗi request” nhưng contract lại là
`DELETE …/members/:userExternalId`, singular. Shape chỉ lộ khi đặt **acceptance scenario**
cạnh **route**.

</Trap>

## Check mà public send duy nhất không thể chạm tới

Membership check thuộc data access—constitution đặt tenant isolation ở đó, và cùng argument
áp dụng cho authorization trong tenant. Check trong một service có thể bị bypass bởi caller
kế tiếp chạm repository trực tiếp. Research note nói sáu caller inherit nó; call graph chỉ
có ba, và caller quan trọng nhất không truyền gì.

```ts
// services/api/src/messages/messages.controller.ts, before this chapter
return this.messages.send(channelId, body);
```

`MessagesController` không khai báo `@Accepts`, nên guard fallback nhận cả hai credential
class và user token vào được. Handler gọi service rồi repository function có `userId`
optional; check lại chỉ chạy khi parameter hiện diện. User vì thế có thể send vào private
channel mà không là member và không gì nhìn thấy.

**Parameter không ai điền vào không encode điều gì.** Argument đúng với signature nhưng
sai với caller; vẽ graph đã tìm ra điều đó.

## Refusal tiết lộ điều nó đang từ chối

Ba task và contract ghi send refusal của private channel là `403 not_a_member`. Một success
criterion lại đòi send trả byte-identical với channel không tồn tại; hai điều không thể
cùng đúng vì 403 nói channel tồn tại.

Private send vì vậy trả not-found envelope. `not_a_member` lại **không có emitter nào trong
chương này**: emitter duy nhất của nó là read-position route trên public channel ở chương
kế, nơi read position là per-member state. Registry ghi rõ để reader sau không phải tìm.

<Trap title="Mười hit nhưng không có emitter">

`grep` `not_a_member` cho mười kết quả, nhưng mọi kết quả là **domain result value**, không
phải wire code. Bulk member removal trả outcome theo user có cùng spelling; service lại
chuyển nó thành `notFound()` một dòng sau. Hai trong ba code chương này register ở tình
trạng ấy: `channel_archived` được gửi, `not_a_member` chờ route chương sau,
`user_banned` chờ ban. Registry là vocabulary, không phải inventory của điều đã nói.

</Trap>

 * as an absent one; the rate limiter added `request_id` to every error body and
 * forced this helper into existence; and there it stayed — one file's private
 * function doing the thing constitution I asks of every endpoint.
 *
 * A correct assertion written once and never generalised is what separates scattered
 * isolation tests from a suite. It lives here so every route can share it, and
 * `messages.itest.ts` imports it back.
 *
 * `request_id` is unique per request BY DESIGN, so two error bodies can no longer be
 * compared whole — and comparing them whole is how a suite proves a foreign resource
 * is indistinguishable from an absent one, which is a tenant-isolation property
 * (constitution I).
 *
 * The id is the one field that reveals nothing about the resource, so it is the one
 * field the comparison must drop. Everything discriminating still has to match
 * exactly.
 *
 * WHY IT ARRIVES IN THIS CHAPTER AND NOT WITH THE HARNESS. The isolation harness
 * owns it by subject — `chapter-map.json` lists it there — and that chapter's page
 * never fenced it, so it was assigned to a chapter and delivered by none. It is here
 * because this is the first chapter whose tests cannot be written without it: three
 * of them compare a private channel's refusal against an absent channel's, and the
 * bodies differ by exactly this field. A file belongs to the chapter that creates it. */
export function withoutRequestId(body: unknown): unknown {
  if (typeof body !== "object" || body === null) return body;
  const rest: Record<string, unknown> = { ...(body as Record<string, unknown>) };
  delete rest["request_id"];
  return rest;
}

//
// `PORT=0` is how a spawned service avoids the fixed-port collisions this repository
// spent four suites removing. It only works if the child says which port it got, and
// a child that logs the value it was PASSED prints `0`.
//
// The api has read the bound address back since the isolation harness. The gateway
// did not, for eleven chapters, and nothing said so — every suite that spawned a
// gateway handed it a fixed port, so the logged value was the value passed in and
// correct by accident. The e2e journey found it the moment it asked: `api up on
// 37763`, then `gateway 1 never became healthy`, which is a health probe against
// port zero.
//
// WHY SOURCE-READING AND NOT A RUNNING PROBE. `main.ts` is excluded from coverage
// (`**/main.ts`) because it is reached by running the service rather than asserting
// on it, and a test that spawns both services to check one log line costs more than
// the whole unit lane. What has to be true is a property of the source: the port
